## 3. 경험치·레벨업

### 3.1. 누가 얼마나 받는가 (결정됨: D19, 2026-10-18)

- **받는 대원**: 승리로 끝나는 순간(`finish(state, "victory")`) HP가 1 이상인 대원. 전투 불능 대원은 받지 않는다.
- **양**: 경험치 총량 `E` = 처치 기록(06 §3.17 `kill`)이 있는 적들의 `exp` 합. 살아 있는 인원 `n`(HP 1 이상인 대원 수, 레벨 상한 대원도 센다). 한 사람 몫 `share = E / n`(정수 나눗셈, 버림). 살아 있는 대원마다 `share`를 받는다. 쓰러진 대원이 있으면 `n`이 작아져 남은 대원이 더 받는다(사용자 결정 D19).
  - 버린 나머지(`E − share × n`)와 상한 때문에 못 받은 양(§3.4)은 다시 나누지 않고 사라진다(제안: 나머지를 칸 순으로 1씩 더 주는 방식은 대원 순서에 따라 받는 양이 달라져 읽기 어렵다).
  - **살아 있는 아군이 없으면 승리로 끝내지 않는다**(조정자 결정, 2026-10-18): `finish(state, "victory")`는 아군이 모두 HP 0이면 `false`를 돌려주고 아무것도 바꾸지 않는다. 도주도 같다. 규칙 전체는 §3.4 「`finish` 거부 규칙」. 자연스러운 끝은 아군 전멸을 먼저 보므로(06 §3.17) 이 거부는 강제 끝(시험, 디버그 `battle_finish`·`simulate`)에서만 생긴다.
  - 그래서 승리 갈래의 분배는 늘 `n ≥ 1`이다. 몫을 계산하는 순수 함수 `GrowthRules.exp_share(total, alive) -> int`는 따로 `alive = 0`이면 0을 돌려준다(나누기 0 방어. 규칙 흐름에서는 생기지 않는다).
  - 예: 네온 쥐 셋(`exp` 12 × 3 = 36): 다섯 살아 있음 → 7(나머지 1 버림), 넷 → 9, 셋 → 12, 둘 → 18, 하나 → 36. 갑충·쥐(40 + 12 = 52): 다섯 → 10(나머지 2), 셋 → 17(나머지 1).
- **근거**: 원작 1편의 몬스터 표는 경험치를 「총계 수치, 파티 인원으로 나눈다」고 적었다(R2 §2.12의 [W04] 원문 「総計数値。PT人数で分配される」. 독립 검토가 2026-10-18에 원문을 열어 확인했고, 이 문서 작성자는 같은 날 HTTP 403으로 직접 열지 못했다). 그 「인원」에 전투 불능 대원을 넣는지는 확인하지 못했다(§13.1). 전투 불능 대원이 전투 경험치를 받지 못하는 것은 V에서 확인된다(R2 §2.12 [W24]). 「살아 있는 인원으로 나눔」은 이 둘을 이은 사용자 결정이고, 버림은 자체 제안이다.
- **받지 않는 경우**: 도주·턴 상한 도주(`turn_cap`)·전멸. 강제 승리(시험·디버그의 `finish(state, "victory")`)에서 처치 기록이 없는 적은 드롭처럼 경험치도 주지 않는다(06 §3.17 「처치 기록이 없는 적은 드롭을 굴리지 않는다」와 같은 기준).
- 경험치 처리는 **난수를 쓰지 않는다.** 그래서 `finish`가 뽑는 난수(드롭 → 한계값, 06 §3.17)의 순서·횟수는 M2와 같다.

### 3.2. 성장 규칙 파일과 경험치 표 (`data/rules/growth.json`)

```json
{
  "level_cap": 30, "initial_sp": 3, "sp_per_level": 1,
  "exp_next": [30, 85, 156, 240, 335, 441, 556, 679, 810, 949, 1094, 1247, 1406, 1571, 1743,
               1920, 2103, 2291, 2485, 2683, 2887, 3096, 3309, 3527, 3750, 3977, 4209, 4445, 4685]
}
```

- `level_cap` 30: 01 §7 「첫 슬라이스 30」.
- `initial_sp` 3·`sp_per_level` 1: 01 §5 「초기 SP 3, 레벨업마다 1」, R2 §2.9(I·IV·V 공개 자료).
- `exp_next[L − 1]`: 레벨 L에서 L + 1로 가는 데 드는 경험치(길이 = `level_cap − 1`). 모든 직업이 같은 표를 쓴다(제안: 원작도 직업별 경험치 곡선 차이를 조사에서 찾지 못했다. IV 초반 곡선은 R2 §2.13).
- 위 값은 `30 × L^1.5`를 반올림한 **자리표시**다(일회용 파이썬 식으로 한 번 만들어 적었다. 규칙 코드는 식을 쓰지 않고 표만 읽는다). 다섯 모두 살아 있으면 Lv2까지 30은 쥐 셋 전투 다섯 번쯤이다(한 번 7). IV(Lv2까지 100, R2 §2.13)보다 짧게 둔 것은 휴대폰 확인 중 레벨업을 보기 쉽게 하려는 것이고 밸런스 판단이 아니다(D15).
- 누적 경험치 `cum(L)` = Lv1에서 L에 닿기까지의 합 = `exp_next[0] + … + exp_next[L − 2]`(`cum(1)` = 0). 아래 값은 위 배열을 다시 더해 확인했다(2판 정정: 1판의 Lv15·20·25 칸은 한 칸씩 밀린 값이었다).

### 3.4. 레벨업 처리

경험치를 더하는 함수는 하나다: `GrowthRules.gain_exp(state, i, amount, events) -> Dictionary`(전투 승리와 디버그 보급이 함께 쓴다, §4.6·§5.7). 돌려주는 사전은 그 대원의 결과(`gained`·`capped`·`from`·`to`·`sp_gained`·`hp_gain`·`tp_gain`)이고 `battle_end`의 대원별 결과(§3.5)에 그대로 복사한다.

**`capped`의 뜻은 하나다**(조정자 판단, 2026-10-18): `capped = gained < amount` — 레벨 상한 때문에 받을 양의 일부·전부를 버렸는가. 상한에 닿았는지는 `to == level_cap`으로 따로 읽는다. 경우: 정확히 상한까지 받음(`amount = cum(level_cap) − exp`) → `gained = amount`·`capped` 거짓·`to = level_cap`. 넘게 받음 → `gained < amount`·`capped` 참. 이미 상한 → `gained` 0, `amount > 0`이면 `capped` 참. `amount` 0(몫 0) → `gained` 0·`capped` 거짓(상한 대원이어도).

1. 대원이 이미 상한이면 아무것도 바꾸지 않는다: `gained` 0, `capped = amount > 0`(받을 양은 버린다).
2. `exp += amount`. `exp ≥ cum(level + 1)`이고 `level < level_cap`인 동안 `level += 1`. 한 번에 여러 레벨이 오를 수 있다.
3. 상한에 닿으면 `exp = cum(level_cap)`으로 자르고 넘친 양은 버린다(넘친 양이 1 이상일 때만 `capped` 참). 그래서 상한 대원의 `exp`는 늘 `cum(level_cap)`이다(저장 검사 §8.3이 이 관계를 본다). `gained` = 실제로 늘어난 누적 경험치(자르기 뒤 − 앞)라서 `amount`보다 작을 수 있다.
4. 레벨이 올랐으면 §6 묶음으로 새 최대 HP·TP를 계산한다. **늘어난 만큼만 현재 HP·TP에 더한다**(`hp_gain = 새 최대 HP − 옛 최대 HP`, `tp_gain = 새 최대 TP − 옛 최대 TP`).
   - **HP와 TP의 조건을 나눈다**(3판, G-A 구현을 받아들임): HP 0 대원은 HP를 0으로 두고 `hp_gain` 0이다(레벨업으로 소생시키지 않는다). TP는 HP와 상관없이 늘어난 만큼 더한다(`tp_gain` = 늘어난 최대 TP). TP에는 생사 뜻이 없고, 더해도 「현재 ≤ 최대」가 그대로 지켜진다. 패시브 배분의 `max_changed`(§4.6)도 같은 규칙이다(`growth_rules.gd:165-168`·`:356-359`, 시험 `test_growth_rules.gd:353-366`). 승리 경험치는 전투 불능 대원이 받지 않으므로 이 갈래는 디버그 `grant_exp`와 HP 0 대원의 패시브 배분에서만 생긴다. 예: HP 0·TP 10인 Lv1 메딕에게 30 → Lv2, HP 0, TP 12(`tp_gain` 2). 전부 회복하지 않는다(제안: 원작의 레벨업 회복은 확인하지 못했다. 늘어난 만큼만 주면 승리 직후 「레벨업으로 회복」이 원정의 자원 판단을 흐리지 않는다, 01 §1.3 「원정 단위의 긴장」).
   - 늘어난 양은 늘 0 이상이다: 최대 HP·TP가 줄어드는 길이 없다(레벨 표 HP·TP 비감소 §3.3, 패시브 `bonus` 비감소 §7.4, 배분 되돌리기 없음 §4.6, 장비 HP·TP 보정 없음 §5.3). 그래서 「현재값 ≤ 최대」가 늘 지켜지고 자르기 규칙이 필요 없다.
5. SP는 따로 저장하지 않는다. 얻은 SP = `initial_sp + (level − 1) × sp_per_level`, 남은 SP = 얻은 SP − 배운 스킬 레벨의 합(§4.1). 레벨이 오르면 남은 SP가 자동으로 는다. `sp_gained` = `(to − from) × sp_per_level`(레벨 차이만으로 보이지 않는다: `sp_per_level`은 0~9다).

- 승리 때 순서(`finish`의 승리 갈래, 제안): 거부 규칙(아래, 거부면 끝) → 드롭(06 §3.17, 난수) → **경험치·레벨업**(대원 칸 순, 난수 없음) → 위험도 0·한계값(난수) → `battle_end` → `battle = null`. 경험치를 드롭과 한계값 사이에 넣어도 뽑는 난수의 순서·횟수는 M2와 같다.
- **`finish` 거부 규칙**(조정자 결정, 2026-10-18; 06 §3.17 `finish` 계약과 §10.1 「끝」 줄에 반영됨): 지금의 기본 거부(`battle` 없음·`pending` 거짓·`wiped` 참·모르는 `outcome`, `battle_rules.gd:588-589`) 뒤, **어떤 부작용보다 먼저**(드롭·경험치·위험도·난수·이벤트) 아래를 본다. 지금 `wiped`에만 있는 검사(구현 전 `battle_rules.gd:590-591`)를 이 한 줄로 바꾼다(구현 `battle_rules.gd:593-595`).

  ```gdscript
  var all_down := b.all_down(BattleUnit.PARTY)
  if (outcome == "wiped") != all_down:
      return false
  ```

  | 요청한 끝 | 살아 있는 대원 있음 | 살아 있는 대원 없음 |
  |---|---|---|
  | `victory` | 받음 | 거부 |
  | `escaped`(`reason` `turn_cap` 포함, `battle_rules.gd:576`) | 받음 | 거부 |
  | `wiped` | 거부(M2 그대로) | 받음 |

  - 거부하면 `false`를 돌려주고 상태·`rng.state`·받은 `events` 배열을 바꾸지 않는다. 요청한 도주를 전멸로 바꾸지 않는다(API 계약은 「받거나 거부」 그대로). 적이 살아 있는 강제 승리는 계속 받는다(06 §3.17).
  - 이유: 받으면 끝 상태가 「모든 대원 HP 0인데 `wiped` 거짓」이 되어 저장 검사(`save_codec.gd:450-451`)가 거부한다. 이 규칙으로 「`finish`가 받은 끝 상태는 늘 저장할 수 있다」가 지켜진다(§10.1). 디버그 길은 `finish`가 `false`면 아무것도 하지 않는다(`battle_layer.gd:573-580`).
- 레벨업은 전투가 끝나는 순간에만 일어나므로 전투 중 능력치가 바뀌지 않는다. 대원 `max_hp`가 바뀌는 것은 `battle`을 지우기 직전이다. 전투 상태의 아군 유닛은 HP·TP를 `Member`에서 읽으므로(`battle_unit.gd:62-86`) 따로 옮길 값이 없다.

- 전투 로그(06 §9.4)에도 `exp`·`level_up` 줄을 남긴다.

## 4. 스킬 트리

### 4.1. SP

- 얻은 SP = `initial_sp + (level − 1) × sp_per_level`(Lv1 3, Lv30 32). 남은 SP = 얻은 SP − Σ(배운 스킬의 레벨). 「스킬 레벨 1을 배움」이 SP 1이다(R2 §2.9 「초기 SP 3과 레벨 상승에 따른 SP 획득」).
- 저장 검사는 Σ ≤ 얻은 SP를 본다(§8.3). 남은 SP를 따로 저장하지 않아 두 값이 어긋날 일이 없다.

### 4.2. 트리 형식 (직업 파일의 `tree`)

```json
"tree": [
  {"skill": "skill.holo_knight.front_guard", "pos": [0, 0], "requires": [], "min_level": 1},
  {"skill": "skill.holo_knight.photon_wall", "pos": [2, 1], "min_level": 5,
   "requires": [{"skill": "skill.holo_knight.defense_protocol", "level": 2},
                {"skill": "skill.holo_knight.shield_mastery", "level": 3}]}
]
```

- `tree`가 직업 파일의 `skills`(06 §5.3)를 대신한다. 배열 순서가 화면 목록 순서이고, 읽은 뒤 `ClassDef.skills`(`battle_data.gd:113`)는 이 순서의 스킬 ID 목록으로 채운다(그것을 쓰는 지금 코드 `party_data.gd:141`이 그대로 돈다).
- **선행 조건 `requires`**: `{skill, level}` 목록, 모두 충족해야 한다(AND). 근거: I 소드맨의 더블 어택은 검·도끼 마스터리 선행을 **함께** 요구한다(R2 §2.9 [W05]). OR 조건은 원작 사례를 찾지 않았고 M2.5에 넣지 않는다.
- **레벨 관문 `min_level`**: 그 스킬의 첫 레벨을 배우려면 대원 레벨이 이 값 이상. 근거: IV의 VETERAN·MASTER 단계는 캐릭터 Lv20·40 관문이고 R2는 「선행 기술과 레벨 관문은 별도 조건」이라고 적었다(R2 §2.9 [W16]). M2.5는 관문을 스킬마다 둔다(IV처럼 트리 단계마다 묶지 않는다, 제안: 스킬 6~8개에 단계 셋은 과하다).
- 선행 조건과 관문은 **첫 레벨(0 → 1)을 배울 때만** 본다. 그 뒤 레벨을 올릴 때는 SP와 최대 레벨만 본다(제안: 원작 화면은 선행을 「해금」으로 보이고, 확인한 자료에 「레벨마다 선행이 다시 필요」한 사례가 없다). 배분은 되돌리지 않으므로(§4.6) 한 번 충족한 선행은 계속 충족된다.
- `pos: [열, 행]`은 화면 격자 칸(열 0~3, 행 0~4). 직업 안에서 겹치지 않는다. 화면은 `requires`마다 선을 그린다(§9.3).
- 순환 방지: `requires`는 `tree`에서 **앞에 나온** 스킬만 가리킨다(읽기 오류). 그래서 순환이 생길 수 없고 검사도 한 번 훑기로 끝난다.

### 4.3. 패시브 스킬 (`effect: "passive"`, 새 종류)

- 원작 트리의 마스터리처럼 능력치를 올리고 다른 스킬의 선행이 된다(R2 §2.9 「마스터리도 단순 공격력 상승만이 아니다. 스킬 선행 조건 … 등을 맡을 수 있다」). 전투 명령으로 쓰지 않는다.
- 레벨 줄은 `bonus` 하나: 그 레벨에서의 **총** 보정(누적이 아니라 그 줄의 값이 곧 보정, 06 §5.4 「레벨마다 한 줄」과 같은 뜻). 키는 `STR`·`INT`·`VIT`·`WIS`·`AGI`·`LUC`·`max_hp`·`max_tp` 가운데 고른다.
- 전투 유닛의 `skills`에는 넣지 않는다(§4.7). 그래서 전투 스킬 목록에 나오지 않고, 패시브 ID로 제출하면 `skill_of`가 `null`이라 `unknown_skill`로 거부된다.

| `skill.nano_medic.nano_mastery` | `WIS` 1/1/2/2/3/4/4/5/6/8, `max_tp` 2/4/6/8/10/13/16/19/22/26 |

- `buff` 스킬의 모든 줄 `kind`가 같다(06 §5.4 「레벨 사이 같은 `kind`」를 지킨다).
- 모든 값은 06 §5.6 공통 값 범위 안이다(`power` ≤ 2000, `chance` ≤ 1000, `turns` 1~9, `value` 방향 범위, `base` ≤ 999, `speed` 100~3000 등). 그래서 06 §3.1 산술 상한 표가 그대로 성립한다.

### 4.6. 배분: 초안·확정·취소

- **화면의 초안**: 스킬 화면에서 「+」를 누르면 화면만 바뀐다(초안, 저장하지 않음). 초안에서 「−」는 **초안으로 올린 레벨만** 내린다(확정한 레벨 아래로는 못 내린다). 「되돌리기」는 초안 전체를 지운다. 대원·탭을 바꾸거나 메뉴를 닫을 때 초안이 있으면 **버리기 확인 창** 「배분을 확정하지 않았다. 버릴까?」(「버리기」 / 「돌아가기」)를 띄운다.
- **확정 확인 창**: 「확정」을 누르면 바로 바꾸지 않고 「SP n을 배분한다. 확정하면 되돌릴 수 없다」(「확정」 / 「돌아가기」)를 띄운다(제안: 되돌릴 수 없는 일을 휴대폰에서 한 번 잘못 눌러 끝내지 않게). 두 확인 창 모두 처음 고른 쪽은 「돌아가기」(키보드 `Enter`만 눌러도 안전한 쪽, §9.4).
- **확정**: 확정 확인 창의 「확정」이 규칙 함수 `GrowthRules.allocate(state, i, levels) -> Array[Dictionary]`를 한 번 부른다. `levels`는 바꿀 스킬의 **목표 레벨**(스킬 ID → 정수) 사전이다.
  - 거부(`rejected{reason}` 하나만 내고 상태·난수 불변, 06 §3.2 원칙): 전투 중(`battle != null` 또는 `encounter.pending`)·전멸(`wiped`) → `not_now`(성장 조작 함수가 함께 쓰는 판정 `growth_rules.gd:474-475`. 올바른 상태에서는 `pending ⇔ battle != null`이라 차이가 없다). 대원 칸 밖, 모르는 스킬·다른 직업 스킬 → `unknown_skill`. 목표가 정수가 아니거나 지금 레벨보다 낮음 → `lower`. 최대 레벨 초과 → `max_level`. 바뀌는 것이 없음 → `unchanged`. 첫 레벨을 배우는 스킬의 선행이 **목표 레벨들로 본 결과**에서 충족되지 않음 → `requires`. 관문 미달 → `min_level`. 올린 합 > 남은 SP → `no_sp`.
  - 선행을 「목표 레벨들로」 보는 이유: 한 초안에서 선행 스킬과 다음 스킬을 함께 올릴 수 있게(사용자가 「+」를 차례로 누른 그대로 확정되게).
  - 통과하면 모두 한 번에 바꾸고 화면은 초안을 지운다(거부되면 초안을 그대로 두고 이유를 알림 줄에). 이벤트 `skills_learned{member, changes: [{skill, from, to}](트리 순), sp_left}`. 패시브가 최대 HP·TP를 바꾸면 §3.4 4단계와 같이 늘어난 만큼 더하고 `max_changed{member, max_hp, max_tp, hp_gain, tp_gain}`를 낸다.
- **화면의 「+」 가능 여부**는 같은 판정을 초안 기준으로 하는 읽기 함수 `GrowthRules.learn_block(defs, i, member, draft, skill) -> String`(`""`·`unknown_skill`(그 직업 트리에 없음)·`max_level`·`requires`·`min_level`·`no_sp`, `growth_rules.gd:310-323`)를 쓴다. `draft`는 스킬 → 초안으로 더한 레벨. 「−」는 `GrowthRules.unlearn_block(…)`(`""`·`no_draft`(초안으로 올린 레벨이 없음)·`requires`, `:328-339`): 그 스킬을 선행으로 삼는 다른 초안 스킬이 첫 레벨을 초안으로 배우는 중이고 「−」 뒤 선행이 깨지면 막는다(이유를 알림 줄에). 확정 때 규칙이 다시 본다.
- **읽기 함수(구현에서 더함, 3판)** — 화면은 이것만 부르고 따로 계산하지 않는다(§11.4):
  - `first_learn_block(class_def, member_level, levels, skill)`(`:229-235`): 첫 레벨(0 → 1)의 선행(`levels`로 본 값)·관문 판정 `""`·`requires`·`min_level`. `learn_block`·`allocate`·`skills_problem`이 함께 쓴다.
  - `skills_problem(db, class_def, level, skills)`(`:241-261`): 배운 스킬 사전 전체의 트리·최대 레벨·선행·관문·SP 검사(`[]` = 문제없음, 아니면 `[스킬 ID 또는 "", 내용]`). 파티 파일의 시작 배분(`party_data.gd:134`)과 저장 검사(`save_codec.gd:446`)가 같은 함수를 쓴다(§8.3 「같은 판정 함수」).
  - `sp_total(defs, level)`·`sp_used(skills)`·`sp_left(defs, member)`(`:115-126`): §4.1 식.
  - 패시브 배분이 최대 HP·TP를 바꾸면 `max_changed`의 증가량은 §3.4 4단계의 HP·TP 규칙을 따른다(HP 0 대원은 `hp_gain` 0, `tp_gain`은 늘어난 만큼, `_refresh_with_gain` `:350-360`).
- **확정 뒤 되돌리기 없음**: 재분배는 휴양(01 §7, 비범위). 「확정」 단추 옆에 「확정하면 되돌릴 수 없다」를 적는다.
- 언제 할 수 있나: 탐색 중 전투·전멸이 아닐 때 어디서나(원작은 미궁 안 캠프 메뉴에서 스킬을 본다, R1 §2.11 「캠프에서 아이템·스킬·상태 확인」). 시간·걸음·난수를 쓰지 않는다.

### 4.7. 전투가 배운 스킬·레벨을 쓰게 바뀌는 곳

- `BattleState.create`(`battle_state.gd:53`)의 `u.skills = defs.party.skills[i]`를 §6 묶음의 `skills`(배운 **액티브** 스킬 → 레벨, 새 사전)로 바꾼다. 이것 하나로 다음이 모두 배운 레벨을 쓴다: 비용(`battle_rules.gd:118-119`), 행동 큐의 레벨(`battle_rules.gd:184` → 실행의 `level_row`), 제출·사용 검사(`battle_rules.gd:66-72`), 화면 스킬 목록(`battle_layer.gd:424-429`), 기대 피해(`battle_policy.gd:162`).
- 지금은 `u.skills`가 정의의 사전을 **그대로 참조**한다(`battle_state.gd:53`, 복사 없음). 새 묶음은 부를 때마다 새 사전을 만든다(06 §8.2 `members()`의 「객체 독립」과 같은 이유: 대원 상태와 전투 유닛이 같은 사전을 나눠 쓰면 한쪽 변경이 다른 쪽에 샌다).
- 전투 중에는 배분·장착을 막으므로(§4.6, §5.7) 전투 중 `u.skills`·능력치는 바뀌지 않는다.
- 적 스킬 레벨(`battle_state.gd:71-73`, 모두 1)은 그대로다.

## 5. 장비

### 5.1. 칸 (제안)

- 대원마다 **4칸**: 칸 0은 무기만, 칸 1~3은 무기가 아닌 장비(방어구·장신구) 아무것이나.
- 같은 종류 제한: `shield`·`body`·`head`·`hands`·`feet`는 한 대원에 하나까지, `accessory`는 둘까지.
- 근거: R2 §2.3 「장비는 통상 4칸을 사용하지만 머리·몸·손·발을 각각 의무 장착하는 방식은 아니다. … I는 장신구 복수 장착이 가능하다」([W16]·[W07] 직접 읽음). 원작별 정확한 칸 규칙(IV 보조 무기 등)은 섞지 않는다(R2 §1 끝 문단). 「장신구 둘까지」는 자체 값이다.
- 빈 칸 허용(무기 칸도). 무기가 없으면 일반 공격은 직업의 `attack`(맨손, §5.3).

### 5.2. 종류와 직업별 장착

- 종류: 무기 `sword`·`staff`(M3에 `bow`·`gun` 등), 방어구 `shield`·`body`·`head`·`hands`·`feet`, 장신구 `accessory`.
- 직업 파일의 `equip_kinds`: 그 직업이 끼는 종류 목록. 장비마다 선택 필드 `only_classes`(직업 ID 목록)가 있으면 **종류 규칙 대신** 그 목록으로 판정한다. 근거: R2 §2.10 「I 무기별 직업 제한, 예외적으로 여러 직업이 장착 가능한 개별 무기도 존재」·「종류별 허용과 개별 예외를 함께 저장할 구조가 필요하다」.

| 직업 | `equip_kinds` |
|---|---|
| 홀로나이트 | `sword`·`shield`·`body`·`head`·`hands`·`feet`·`accessory` |
| 블레이드 듀얼리스트 | `sword`·`body`·`head`·`hands`·`feet`·`accessory` |
| 나노 메딕 | `staff`·`body`·`head`·`hands`·`feet`·`accessory` |
| 글리프 위저드 | `staff`·`body`·`head`·`feet`·`accessory` (손 장비 없음: 직업 제한 시험용) |

### 5.3. 장비가 주는 것

- `atk`·`matk`·`def`·`mdef`(각 0~999): 장착한 장비의 합이 전투 유닛의 `gear`가 된다 → 피해식 `A`·`D`(`battle_rules.gd:451-452`, 06 §3.9).
- `stats`: 능력치 보정(`STR`~`LUC`, −99~99. 음수는 무거운 갑옷의 AGI 같은 대가).
- `resist`·`ailment_vuln`·`bind_vuln`: 받는 배율의 **더하기 보정**(‰, −3000~3000). 예: 열 −300이면 직업 배율 1000 → 700(받는 열 피해 0.7배). 더하기로 정한 이유(제안): 곱하기는 장비 두 개가 같은 보정을 줄 때 순서·버림 문제가 생기고(06 §3.9 곱 순서 문제와 같다) 화면에 「열 −30%」로 그대로 보이기 쉽다.
- 무기만 `element`(필수, 속성 6종): 일반 공격의 속성. R2 §2.10 「무기 종류와 피해 속성은 별도다」 — 그래서 종류(`sword`)에서 속성을 추론하지 않고 무기마다 적는다(06 §5.4의 「속성에서 추론하지 않는다」와 같은 원칙). 무기가 없으면 직업 `attack.element`.
  - **공유 객체 주의**: 직업의 일반 공격은 정의를 읽을 때 한 번 만든 `SkillDef`(`RefCounted`)이고(`battle_data.gd:76-83·480-492`), 지금 전투 유닛은 그 객체를 그대로 가리킨다(`battle_state.gd:54`). 그 객체의 `element`를 바꾸면 같은 직업의 다른 대원(듀얼리스트 A·B)과 정의 자체가 함께 바뀐다. 그래서 §6 묶음은 대원마다 **새 `SkillDef`**(직업 일반 공격의 필드를 복사하고 `element`만 무기 값)를 만들고, `ClassDef.attack`은 읽기만 한다. 무기가 없거나 무기 속성이 직업 값과 같아도 복사본을 쓴다(갈래를 하나로 둔다).
- 일반 공격의 다른 값(`stat` STR·`power` 100·`accuracy` 950·근접 등, 06 §5.3)은 그대로다. 무기 종류로 원거리 일반 공격을 하는 것(활)은 M3.
- **HP·TP 보정 없음**(M2.5): 장비를 바꿀 때 최대 HP가 줄면 현재 HP를 어떻게 자를지(원작 규칙 미확인)가 따로 필요하다. 장비 정의의 `stats`에 `max_hp`·`max_tp`가 있으면 읽기 오류다.

- 기능 시험이 쓰는 갈래가 모두 하나 이상 있다: 무기 속성 바뀜(이온 세이버), 능력치 보정 양수·음수, 받는 배율 보정(속성·상태·부위), 종류 규칙 밖으로 넓히는 예외(택티컬 배턴: 홀로나이트는 원래 `staff`를 못 낀다), 종류 규칙보다 좁히는 예외(메시 아머: 메딕·위저드는 `body`를 끼지만 이것은 못 낀다), 직업 종류 제한(위저드의 손 장비), 같은 종류 제한(방패 둘, 장신구 셋).
- 01 §9의 「장비 약 25종」은 수직 슬라이스(M3) 목표다. 상점이 생기면 `얻는 길`을 상점 해금으로 옮긴다.

### 5.6. 소지품

- **장비 가방** `ExplorationState.gear_bag`(장비 ID → 개수 1~99, 0개는 키 없음): 장착하지 않은 장비만 센다. 장착한 장비는 대원 칸에만 있다(같은 장비가 두 곳에 세어지지 않게).
- **소재** `materials`(06 §3.17, 1~9999)는 그대로 따로 둔다. 화면은 한 「소지품」 탭에 두 묶음(장비·소재)으로 보인다.
- 따로 두는 이유(제안): 소재는 저장 2판의 필드·검사(06 §8.5)가 있고 상한(9999)·드롭 포화 규칙이 이미 정해졌다. 장비는 상한 99(원작의 한 칸 최대 99 관례를 따랐으나 조사 문서에는 근거가 없어 자체 값), 장착 이동이 있다. 원작의 공용 가방 칸 수(작품마다 다름, R1 §2.5는 소재 경제만 다룸)는 상점과 함께 M3에서 정한다.
- 가방이 99인 장비를 벗기면 넘치므로 그 장착 변경은 거부한다(`bag_full`, §5.7). 임시 보급은 99에서 멈춘다(포화, 06 §3.17 소재 상한과 같은 방식).

### 5.7. 장착·임시 보급 규칙 함수

- `GrowthRules.equip(state, i, slot, item_id) -> Array[Dictionary]`. `item_id`가 `""`이면 빼기.
  - 거부(`rejected{reason}`, 상태 불변): 전투 중(`pending` 포함, §4.6)·전멸 → `not_now`. 대원 칸 밖 → `unknown_member`(3판). 칸 밖 → `bad_slot`. 모르는 장비 → `unknown_item`. 가방에 없음 → `not_in_bag`. 칸 0에 무기 아님·칸 1~3에 무기 → `slot_kind`. 직업이 못 낌 → `class`. 같은 종류 제한(바꿀 칸의 지금 장비는 빼고 셈) → `kind_limit`. 벗겨 낼 장비를 가방에 넣으면 99를 넘음 → `bag_full`. 빈 칸 빼기·그 칸에 이미 있는 장비를 다시 끼기 → `unchanged`(3판에서 뒤의 경우를 더함). 구현 `growth_rules.gd:410-453`.
  - 판정 순서는 `equip_block(defs, i, member, bag, slot, item_id)`(`:410-429`, 가방 포함, 화면도 이것으로 막는다)의 순서다: `bad_slot` → (빼기면 `unchanged`·`bag_full`) → `unknown_item` → `unchanged` → `not_in_bag` → `slot_kind`·`class`·`kind_limit` → `bag_full`.
  - 통과: 칸의 지금 장비는 가방 +1, 새 장비는 가방 −1(0이면 키를 지움), 칸에 새 장비. 이벤트 `equipped{member, slot, item, removed}`.
- `GrowthRules.supply(state, item_id, n)`(임시 보급, 디버그 전용): `n` 1~99, 가방 개수 포화 99. 이벤트 `supplied{item, amount, capped}`. 거부: 전투 중·전멸 → `not_now`, 모르는 장비 → `unknown_item`, `n`이 1~99 정수가 아님 → `bad_amount`(3판, `:457-468`).
- `GrowthRules.grant_exp(state, i, n)`(임시 보급, 디버그 전용): `n` 1~999,999, §3.4 `gain_exp`를 그대로 부른다(살아 있는지 보지 않는다. HP 0 대원은 레벨이 오르고 HP는 0, TP는 늘어난 만큼, §3.4). 거부: 전투 중·전멸 → `not_now`, 대원 칸 밖 → `unknown_member`, `n`이 범위 밖·정수 아님 → `bad_amount`(3판, `:213-223`).
- **읽기 함수(구현에서 더함, 3판)**: `slot_block(db, class_def, equip, slot, item_id)`(`:367-384`, 가방을 보지 않는 `""`·`unknown_item`·`slot_kind`·`class`·`kind_limit` — 장비 목록에서 끼울 수 없는 줄의 이유), `equip_problem(db, class_def, equip)`(`:397-405`, 칸 넷 전체 검사 — 파티 파일의 시작 장비 `party_data.gd:143`과 저장 검사 `save_codec.gd:460`이 같은 함수). `equip_problem`은 칸 0부터 차례로 보므로 같은 종류 제한 오류는 **처음 충돌하는 칸**을 가리킨다(예: 칸 1의 원래 방패와 칸 3에 더한 방패면 칸 1).
- 대원 칸 번호는 장착·보급처럼 `unknown_member`로 거부하되, `allocate`는 1판 그대로 `unknown_skill`이다(§4.6).
- 셋 다 난수·시간·걸음을 쓰지 않는다. 바꾼 뒤 자동 저장(§8.5).
- **임시 보급을 일반 화면에서 숨긴다**(제안): 디버그 주소(`?debug=1`, `web_bridge.gd:57-59`)이거나 네이티브 디버그 실행(`OS.is_debug_build()`)일 때만 소지품 탭에 「임시 보급(시험용)」 단추를 보인다. 일반 주소의 플레이어에게는 「장비는 시작 장비뿐」인 상태가 자연스럽고, 상점(M3)이 들어오면 그 길이 정식 획득처가 된다. 휴대폰 실기 확인은 디버그 주소로 한다(§10.5). 보급으로 생긴 장비·경험치는 일반 저장에 그대로 남는다(표시하지 않는다. 대안은 §13.2).

## 6. 대원 능력치 묶음 — 한 함수

`GrowthRules.profile(defs, i, member) -> Dictionary`(새 사전, 읽은 뒤 바꾸지 않음. 구현 `growth_rules.gd:24-84`). 전투 시작(`BattleState.create`), 최대 HP·TP 계산(새 게임·저장 읽기·레벨업·패시브 배분), 상태 화면이 모두 이것만 부른다. 다른 곳에서 능력치를 따로 더하지 않는다.

```
row       = 직업.levels[member.level]
passive   = 배운 패시브 스킬마다 levels[레벨 − 1].bonus 의 합
stats[k]  = clamp(row[k] + passive[k] + Σ장비.stats[k], 1, 999)              k ∈ STR·INT·VIT·WIS·AGI·LUC
max_hp    = clamp(row.hp + passive.max_hp, 1, 9999);  max_tp = clamp(row.tp + passive.max_tp, 1, 9999)
gear[g]   = clamp(Σ장비[g], 0, 999)                                          g ∈ atk·matk·def·mdef
resist[e] = clamp(직업.resist[e] + Σ장비.resist[e], 0, 3000)                  ailment_vuln·bind_vuln 도 같은 식
attack    = 새 SkillDef(직업 일반 공격의 복사본), element = 무기.element(무기가 있으면)   ClassDef.attack 은 바꾸지 않는다(§5.3)
skills    = {배운 액티브 스킬 → 레벨}                                         패시브·레벨 0은 넣지 않는다
breakdown = STR…LUC·max_hp·max_tp 마다 {base, passive, equip, total} (화면 표시용, max_hp·max_tp 의 equip 은 늘 0)
weapon    = 칸 0 의 장비 ID 또는 "" (화면 표시용)
```

- 자르는 범위가 06 §5.6의 정의 범위(능력치 1~999, 장비 0~999, 배율 0~3000, HP·TP 1~9999)와 같아서 06 §3.1 산술 상한 표(`A ≤ 1998` 등)가 그대로 성립한다. 범위를 넓히려면 06 §3.1 표를 먼저 다시 계산한다.
- 더하는 순서는 결과에 영향이 없다(정수 합 뒤 한 번 자름).
- `BattleState.create`(구현 `battle_state.gd:40`에서 묶음을 부름)는 대원마다 이 묶음으로 `u.stats`·`u.gear`·`u.resist`·`u.ailment_vuln`·`u.bind_vuln`·`u.skills`·`u.attack`을 채운다. `u.row`·`u.name_key`는 지금처럼 파티 정의에서(대열 교체는 M3).
- `GameDefs.member_stats(i)`(구현 전 `game_defs.gd:82-83`)는 쓰는 곳을 이 묶음으로 바꾸고 지운다(레벨 표 줄만 보는 함수가 남으면 장비·패시브를 빠뜨린 값을 읽는 곳이 생긴다). 3판: 지웠다.
- **시작 대원** `GrowthRules.start_member(defs, i)`(`:101-110`): 시작 파티 정의의 레벨·`exp = cum(레벨)`·시작 배분·시작 장비, 이 묶음의 최대 HP·TP, HP·TP 가득. 새 게임(`GameDefs.members()`)과 저장 이전(§8.4)이 같은 함수를 쓴다(§8.1). `refresh_max(defs, i, member)`(`:93-96`)는 최대 HP·TP만 다시 담고 현재값은 건드리지 않는다.
- **승리 경험치** `GrowthRules.victory_exp(state, battle, events)`(`:183-209`): `finish`의 승리 갈래가 드롭 다음에 부르는 분배(§3.1·§3.4·§3.5). `exp_share(total, alive)`(`:133-134`)로 몫을 내고 대원마다 `gain_exp`를 부른 뒤 `battle_end`에 더할 성장 필드를 돌려준다.

### 7.3. 직업 파일

```json
{
  "id": "class.holo_knight", "name_key": "class.holo_knight",
  "levels": {"1": {"hp": 60, "tp": 30, "STR": 15, "INT": 8, "VIT": 19, "WIS": 13, "AGI": 11, "LUC": 14}, "…": {}, "30": {}},
  "attack": {"element": "slash", "range": "melee"},
  "resist": {}, "ailment_vuln": {}, "bind_vuln": {},
  "equip_kinds": ["sword", "shield", "body", "head", "hands", "feet", "accessory"],
  "tree": [{"skill": "skill.holo_knight.front_guard", "pos": [0, 0], "requires": [], "min_level": 1}]
}
```

- `levels`: 키가 정확히 `"1"`~`"level_cap"`(빠진 레벨·넘는 레벨 거부). 줄 필드는 06 §5.3 그대로(`hp`·`tp`·능력치 6, 06 §5.6 범위). `hp`·`tp`는 레벨이 오를 때 줄지 않는다(§3.3, 줄면 읽기 오류 「levels.L.hp: 앞 레벨보다 작다」).
- `attack.element`는 「무기가 없을 때」의 속성이 된다(§5.3).
- `equip_kinds`: 종류 열거값, 중복 없음, 무기 종류 하나 이상.
- `tree` 항목: `skill`·`pos`·`requires`·`min_level` 모두 필수.

### 7.4. 스킬

- 액티브 스킬은 06 §5.4 형식 그대로. 줄 수(= 최대 레벨)는 1~10.
- 패시브: 스킬 단계 필드는 `id`·`name_key`·`user`(`party`만)·`effect`(`passive`)·`levels` **만**(06 §5.4의 「모두」 줄의 `range`·`target`·`parts`·`priority`·`speed`와 피해 필드는 있으면 오류). 줄 필드는 `bonus` **만**(`tp` 없음). `bonus` 키는 §4.3의 8개 가운데 하나 이상, 모든 줄의 키 집합이 같고 값은 레벨이 오를 때 줄지 않는다(줄면 배분 때 최대 HP가 줄어 HP 자르기가 생긴다).
- `BattleDb`의 `EFFECTS`·`USER_EFFECTS["party"]`(`battle_data.gd:11·38-41`)에 `passive`를 더한다. `EFFECT_TARGETS`에는 넣지 않는다(대상이 없다). 적 스킬은 `passive`를 못 쓴다.

### 7.5. 장비 `data/items/equipment.json`

```json
{"equipment": [
  {"id": "equip.ion_saber", "name_key": "equip.ion_saber", "kind": "sword",
   "atk": 22, "matk": 0, "def": 0, "mdef": 0, "element": "volt",
   "stats": {}, "resist": {}, "ailment_vuln": {}, "bind_vuln": {}},
  {"id": "equip.tactical_baton", "name_key": "equip.tactical_baton", "kind": "staff",
   "atk": 12, "matk": 0, "def": 0, "mdef": 0, "element": "bash",
   "stats": {}, "resist": {}, "ailment_vuln": {}, "bind_vuln": {},
   "only_classes": ["class.nano_medic", "class.holo_knight"]}
]}
```

- 필수: `id`·`name_key`·`kind`·`atk`·`matk`·`def`·`mdef`·`stats`·`resist`·`ailment_vuln`·`bind_vuln`(빈 객체 가능). 무기 종류면 `element` 필수, 아니면 있으면 오류. `only_classes`만 선택(없으면 종류 규칙. 06 드롭의 `if`와 같은 선택 필드).
- `stats` 키 ⊆ 능력치 6종(값 −99~99, 0은 적지 않는다), `resist` 키 ⊆ 속성 6종, `ailment_vuln` ⊆ 상태 3종, `bind_vuln` ⊆ 부위 3개(값 −3000~3000, 0은 적지 않는다).
- **0과 모르는 키**(3판, 구현 `battle_data.gd:470-474`·`:1225-1243`): `stats`·`resist`·`ailment_vuln`·`bind_vuln`의 값 0은 읽기 오류 「0 은 적지 않는다(보정이 없으면 키를 뺀다)」. `stats`의 모르는 키(예: `max_hp`)는 「능력치 6종(…)만 받는다(HP·TP 보정은 없다, 07 §5.3)」 오류다.
- `only_classes`: 직업 ID, 1개 이상, 중복 없음.

### 7.6. 파티 파일 3판 (시작 파티)

```json
{"members": [
  {"id": "holo_knight", "name_key": "member.holo_knight", "class": "class.holo_knight", "level": 1, "row": "front",
   "skills": {"skill.holo_knight.front_guard": 1, "skill.holo_knight.aegis_cover": 1, "skill.holo_knight.defense_protocol": 1},
   "equip": ["equip.training_sword", "equip.training_shield", "equip.padded_coat", null]}
]}
```

- `gear`(고정 수치)를 없애고 `equip`(길이 4, 장비 ID 또는 `null`)을 둔다(`party_data.gd:6` `MEMBER_KEYS`).
- `skills`는 **시작 배분**이다. 트리 규칙(선행·관문·최대 레벨)과 SP(Σ ≤ 그 레벨의 얻은 SP)를 지켜야 한다. 시작 장비도 장착 규칙(§5.7의 칸·직업·종류 제한)을 지켜야 한다. 시작 경험치는 `cum(level)`.
- 시작 파티의 스킬은 M2와 같고 글리프 위저드만 부식 글리프를 뺀다(§4.4). 시뮬레이션의 파티(`tests/sim/sim_lib.gd:258-278`)는 이 파일의 대원을 복사하므로 형식만 따라가면 된다.
- 스킬 레벨 범위는 지금 대원 레벨과 같은 `level`(1~99, `party_data.gd:92`)을 쓰는데, 새 이름 `skill_level`(1~10)로 나눈다(§7.7).

### 7.8. 검사 (읽을 때 거부할 것)

06 §5.6에 더한다. 모든 오류에 파일·필드 경로.

- 자료형·필수·모르는 필드: §7.2~§7.6 형식대로.
- ID: `equip.` 접두사, 파일 전체에서 중복 없음, 참조(트리의 스킬·선행 스킬, 장비의 `only_classes`, 파티의 장비)가 있음, `name_key`가 `ko.json`에 있음.
- 관계:
  - 직업 `levels`의 키가 1~`level_cap` 전부, `hp`·`tp`가 레벨마다 줄지 않음(§3.3). `exp_next` 길이 = `level_cap − 1`.
  - 트리: 스킬 ID가 그 직업 접두사(`skill.<직업 이름>.`)이고 `user: party`, 트리 안 중복 없음, `pos` 중복 없음, `requires`는 트리에서 앞에 나온 스킬이고 `level` 1~그 스킬의 최대 레벨, 같은 스킬을 두 번 요구하지 않음, `min_level` 1~`level_cap`. 어느 트리에도 없는 파티 스킬은 경고(06 §5.6 「쓰이지 않는 스킬」).
  - 한 스킬이 두 직업 트리에 있으면 오류(지금 범위에서는 접두사로 막힌다).
  - 패시브: §7.4.
  - 장비: §7.5. 무기 종류 장비의 `element`.
  - 파티: 대원 레벨 1~`level_cap`, 시작 배분이 트리 규칙·SP를 지킴, 시작 장비가 장착 규칙을 지킴, 장비 4칸.
  - 시작 배분·시작 장비 검사는 저장 검사와 같은 함수(`GrowthRules.skills_problem`·`equip_problem`, §4.6·§5.7, `party_data.gd:134·143`)다. 같은 종류 제한 오류는 처음 충돌하는 칸을 가리킨다(§5.7).
- 경고(실패 아님): 어느 직업도 낄 수 없는 장비, 어느 트리에도 없는 파티 스킬.

### 8.3. 저장 검사 추가 (3판, 모두 필수)

| 경로 | 자료형·범위 | 관계 |

### 8.4. 이전: 2판 → 3판, 1판 → 3판

공통 원칙(06 §8.6): 원본을 **그 판 규칙으로 먼저 다 검사**하고, 통과한 임시 상태에서만 옮기고, 원본 `saved_at`·`generation`으로 3판 `encode`(`encode(s, saved_at, generation)`)한 뒤 3판 읽기를 그대로 거친 결과만 돌려준다. 입력 글과 `defs`만 읽고 공유 상태를 바꾸지 않는다. 같은 글은 몇 번 읽어도 같은 결과·같은 해시. `LoadResult.from_schema`는 원본 판(1·2). 디스크의 파일은 이전 때 바꾸지 않는다(`.bak` 후보 복구도 06 §8.6 그대로).

**성장 기본값**: 이전한 대원은 모두 시작 파티 정의의 값을 받는다 — 레벨(1), `exp = cum(레벨)`, 시작 배분, 시작 장비(§7.6). `gear_bag`은 `{}`. 이 값은 `GameDefs.members()`와 같은 함수가 만든다(새 게임과 이전이 같은 시작 값을 쓴다).

**2판 → 3판** (`(2, "m2")`):

1. 머리 검사.
2. **2판 검사**: 지금의 2판 읽기 전부(대원 `id`·`hp`·`tp`, `materials`, `battle`, M1 필드와 관계)를, 이전 함수 안에 고정한 **2판 대원 표**로 한다: `holo_knight` 60/30, `blade_duelist` 52/32, `blade_duelist_2` 52/32, `nano_medic` 42/54, `glyph_wizard` 40/60(최대 HP/TP, 칸 순서, 06 §6.1). 정의에서 읽지 않는 이유: 이 뒤로 정의의 Lv1 줄·파티 파일이 바뀌어도 2판 검사가 흔들리지 않게(06 §8.6이 1판 표를 고정한 것과 같다). 2판 `battle`은 `BattleState.check_dict`로 **검사만** 하고 전투 객체는 아직 만들지 않는다(그 검사는 대원 수·HP만 쓴다, `battle_state.gd:213-260`).
   - **지금 파티가 2판 파티와 다르면 거부**(3판, G-A 구현을 받아들임): 2판 검사가 통과한 뒤, 지금 정의의 대원 ID 목록이 고정 2판 표의 ID·칸 순서(`holo_knight`·`blade_duelist`·`blade_duelist_2`·`nano_medic`·`glyph_wizard`)와 다르면 「2판 이전 실패: 지금 파티가 2판 파티(5명)와 다르다」로 거부한다(`save_codec.gd:245-247`). 2판 칸 순서의 HP·TP를 다른 대원에게 잘못 옮기지 않는 보수적 실패다. 지금 상태·정의는 바뀌지 않는다.
3. **대원 옮기기**: 성장 기본값, 최대 HP·TP = §6 묶음, `hp' = min(hp, 새 최대)`·`tp' = min(tp, 새 최대)`(시작 파티 Lv1은 최대가 2판 표와 같아 값이 바뀌지 않는다. `min`은 정의가 바뀐 경우의 안전장치이고 1 이상인 HP를 0으로 만들지 않는다).
4. **전투 붙이기**: 2판 `battle` 사전이 있으면 3단계 대원으로 `BattleState.from_dict`(난수 없음). 전투를 새로 시작하지 않는다.
5. **3판 재검사**(원본 머리).

**1판 → 3판** (`(1, "m1")`, 2판 문서를 거치지 않는다):

1. 머리 검사.
2. **1판 검사**: 지금과 같다(06 §8.6 2단계, 고정 1판 대원 표 `save_codec.gd:11`). 이 단계 전에는 아무 값도 계산하지 않는다.
3. **대원 옮기기**: 칸 순서로 대원 ID를 옮기고(칸 2 `rail_ranger` → `blade_duelist_2`) 성장 기본값을 넣는다. 새 최대 HP·TP = §6 묶음(시작 파티 Lv1이라 직업 Lv1 줄과 같다). `hp' = ceil(hp × 새 최대 / 옛 최대)`(정수 `(hp × 새 + 옛 − 1) / 옛`, 06 §8.6 3단계), `tp'` = 새 최대 TP. `materials` `{}`, `battle` `null`.
4. **전투 시작 — 1판 `pending`이 참일 때만, 정확히 한 번**: 3단계가 끝난 임시 상태(2단계가 복원한 1판 `rng.state`)에서 `BattleRules.start(임시, BattleRules.pick_formation(임시))`를 한 번 부른다. 성장 값이 들어간 뒤라 `BattleState.create`의 §6 묶음이 옮긴 대원으로 계산된다. 이 뒤로 이전은 난수를 쓰지 않는다(3판 `encode`·읽기에는 난수가 없다). 시작이 거부되면 이전 실패로 오류를 돌려준다.
5. **3판 재검사**(원본 머리).

- 바뀌는 코드: 지금 `migrate_v1`(`save_codec.gd:181-215`)은 옛 형식의 `Member`를 만든 뒤(`:194-200`) 전투를 시작하고(`:205-209`) 지금 `SCHEMA`로 `encode`한다(`:210`, `encode`는 늘 `SCHEMA`를 쓴다 `:58-64`). 3판에서는 「대원 ID·성장 값·최대치·HP 비율 → 전투 시작 한 번 → 3판 encode」 순서여야 `create`가 성장 값 없는 대원을 만나지 않는다. 1판 경로가 2판 이전을 다시 부르거나 전투 시작을 두 번 하는 구조로 만들지 않는다.

| 값 보존 | 대원 HP·TP, `materials`, `battle` 사전(정규화한 JSON이 원본과 같음), `rng.state`, M1 필드(위치·방향·지도·세계·위험도·걸음·전멸). 전투 유닛의 입력값(능력치·`gear`·속성 배율·취약도·일반 공격 속성)이 06 §6.1 표와 같음(시작 장비 합, §5.4) |

| 잃는 것 | **글리프 위저드의 부식 글리프**: 시작 배분(SP 3)에 들지 않아(§4.4) 옮긴 위저드는 배우지 않은 상태다. 이전 전 합법이던 부식 글리프 명령은 이전 뒤 `unknown_skill`로 거부된다(`battle_rules.gd:66-72`). 이미 적에게 걸린 독 상태는 전투 상태라 남는다. 받아들이는 이유: 공개 전이라 실제 사용자 저장이 없다(조정자 결정). Lv3부터 SP로 다시 배울 수 있다(시작 배분 3 + 글리프 마스터리 1 + 부식 글리프 1 = SP 5, Lv3의 얻은 SP가 5) |
| 새로 생김 | 대원 성장 필드, `gear_bag`. 그 뒤 승리하는 턴의 `exp`·`level_up` 이벤트와 `battle_end`의 성장 필드(§3.5). 이전 전후 비교에서 빼고 따로 확인한다 |

- 1판 → 3판도 같은 정책이다(1판에는 스킬·소재·전투 상태가 없다).

### 8.5. 자동 저장 시점 (06 §8.7에 더함)

배분 확정, 장착 변경, 임시 보급. 전투 끝의 레벨업은 이미 「턴 제출 확정 뒤」 자동 저장에 들어 있다. 초안은 화면 것이라 저장하지 않는다(새로고침하면 사라진다).

## 9. 화면 (G-B)

### 9.1. 여는 곳·막는 때

- 탐색 화면 위 줄에 「파티」 단추(64×64, 지도 단추 왼쪽: `x = view_w − 3 × 64 − 28`, `dungeon_screen.gd:939-942` 배치에 이어서). 키보드 `P`(물리 키, `project.godot` InputMap에 `open_party` 추가, 05 §9.3).

### 9.4. 입력 입구 (05 §9.3, 06 §9.5와 같은 원칙)

- 파티 메뉴는 탐색 행동 입구의 「창 열림」 조건이다(`dungeon_screen.gd:201` `_input_blocked`, `:302` `_check_windows`에 더함). 열려 있는 동안 이동·회전·조사·지도 편집 요청을 미리 받지 않고 버린다.
- 열고 닫을 때 미리 받은 이동 입력·누르고 있던 키 승인을 지운다. 메뉴를 닫은 뒤 누르고 있던 이동 키가 걸음으로 이어지지 않는다.
- 메뉴 안의 모든 입력(단추·노드·목록 줄·키보드)은 파티 메뉴의 한 함수(`handle(kind, arg)`, 전투 층 `battle_layer.gd:238`과 같은 꼴)로 온다. 확인 창(버리기·확정)이 떠 있으면 그 창 입력만 받는다. 한 프레임 한 입력.
- 단추는 포커스를 받지 않는다(`FOCUS_NONE`). 포인터 소유권: 누르기가 시작된 곳이 끝까지 가진다(목록·트리에서 끌다가 탭 위에서 떼도 탭이 바뀌지 않음). 흉내 낸 마우스와 터치를 두 번 처리하지 않는다. 누르고 있기 반복 없음(「+」를 길게 눌러도 한 번).
- **문맥이 바뀌면 눌려 있던 포인터를 모두 취소한다**(06 4판 §9.7 「입력」과 같은 규칙): 확인 창이 뜨거나 닫힐 때, 대원·탭이 바뀔 때, 장비 목록이 열리거나 닫힐 때, 메뉴를 열고 닫을 때. 취소된 누르기는 뗄 때 아무 일도 하지 않는다(예: 「+」를 누른 채 `F`로 확정 창을 띄운 뒤 떼도 「+」가 되지 않고, 창 단추도 눌리지 않는다). 메뉴 배경은 포인터를 막아 뒤의 지도·이동 단추에 닿지 않게 한다.
- **키보드만으로 끝까지**(물리 키, 포커스 대신 메뉴가 가진 **커서**를 쓴다. 누르기·클릭도 커서를 그 자리로 옮긴다):

| 어디서 | 키 | 동작 |
|---|---|---|
| 어디서나(확인 창 밖) | `1`~`4` | 탭(상태·스킬·장비·소지품) |
| | `Q` / `E` | 앞·다음 대원(원작의 대원 넘기기 단추 자리. 메뉴가 열린 동안 평행 이동은 막혀 있다) |
| | `Esc`·`P` | 한 단계 뒤로: 장비 목록 → 칸, 그 밖에는 메뉴 닫기(초안이 있으면 버리기 확인 창) |
| 스킬 탭 | `↑`·`↓`·`←`·`→` | 트리 격자에서 그 방향으로 가장 가까운 노드로 커서(같은 행·열을 먼저, 없으면 그대로) |
| | `Enter`·`Space` | 커서 노드 「+」 |
| | `Backspace` | 커서 노드 「−」 |
| | `R` | 「되돌리기」(초안 전체) |
| | `F` | 「확정」 → 확정 확인 창 |
| 장비 탭 | `↑`·`↓` | 칸 넷 또는 오른쪽 목록 줄 |
| | `Enter`·`Space` | 칸에서는 그 칸의 목록으로, 목록 줄에서는 장착(「빼기」 줄이면 빼기)한 뒤 목록을 닫고 커서를 그 칸으로 |
| | `Backspace` | 커서 칸의 장비 빼기 |
| 상태·소지품 탭 | `↑`·`↓` | 줄 이동·내리기. 소지품의 임시 보급 줄(디버그)에서 `Enter` = 「+1」·「경험치」 |
| 확인 창 | `←`·`→` | 두 단추 사이(처음은 「돌아가기」) |
| | `Enter`·`Space` | 고른 단추 |
| | `Esc` | 「돌아가기」(창만 닫고 초안은 그대로) |

  - **메뉴가 열린 동안 모든 키 누름을 삼킨다**(전투 층과 같은 방식: `battle_layer.gd:332-338`이 눌림을 모두 처리됨으로 표시하고, 06 4판 §9.7 「키는 … 열려 있는 동안 모든 키를 삼킨다」). 위 표에 없는 키, 반복(echo), `Ctrl`·`Alt`·`Meta`가 눌린 키는 삼키되 아무것도 하지 않는다. 뗌은 삼키지 않는다(탐색 화면이 누르고 있던 키 승인을 지우는 길 `dungeon_screen.gd:318-322`을 그대로 둔다).
  - 탐색 화면 쪽도 막는다(두 겹): `_unhandled_input`(`dungeon_screen.gd:314-355`)의 전투 층 검사(`:326-327`) 바로 뒤에 「파티 메뉴가 열려 있으면 돌아감」을 둔다. 지금 이 함수의 `open_menu`(`Esc`, `:328-334`)·`map_undo`(`Ctrl+Z`, `:337-340`)·`toggle_map`(`M`, `:341-344`) 분기는 `_input_blocked()`를 보지 않고 바로 실행되므로(`_input_blocked`는 이동 키 갈래 `:345-352`만 본다), `_input_blocked`를 넓히는 것만으로는 막히지 않는다. 휴식 `R`(`:353-355`)·이동 키도 이 검사 뒤에 있어 함께 막힌다.
  - 그래서 메뉴 뒤에서 `Esc`가 주 메뉴를 열거나, `M`이 지도를 접거나, `Ctrl+Z`가 지도 편집을 되돌리거나, `R`·`Q`·`E`·`Space`·방향키가 탐색 행동을 만드는 일이 없다. 메뉴의 `Esc`·`P`는 메뉴 자신이 처리한다(위 표).
  - `Tab`은 쓰지 않는다(웹에서 브라우저 포커스 이동과 겹칠 수 있다. 확인하지 않았다).
- 메뉴가 열린 동안 브라우저 포커스를 잃으면 미리 받은 입력을 지운다(05 §9.3).

### 9.5. 탐색 상태 칸

## 10. 시험 (모두 기능 확인, D15)

승패·특정 시드의 전투 결과·밸런스 범위를 기대값으로 두지 않는다. 난수가 끼는 곳은 결과를 고정하지 않고 「이벤트가 있고 규칙대로 적용됐는지」를 본다. 경험치·레벨업·배분·장착·저장은 난수가 없으므로 정확한 값으로 본다.

### 10.1. 규칙 시험 (`tests/test_growth_*.gd`, G-A)

시험용 정의는 06 §10.1처럼 코드에서 사전으로 만들어 검사까지 거친다(`BattleDb.parse`). 실제 `data/`도 따로 읽어 오류 0·경고 0.

**확률을 확정하는 구성**(D15: 특정 시드의 성공에 기대지 않는다). 「걸림」「맞음」 갈래를 꼭 지나야 하는 시험은 규칙이 **뽑지 않고** 성공하는 상태를 만든다(06 §3.1 `roll(p)`: `p ≥ 1000`이면 뽑지 않고 참).
- 명중: 대상이 수면이거나 스킬이 필중이면 판정하지 않는다(06 §3.8). 아니면 대상 AGI를 1로 둔다 → `hit_p`(`battle_calc.gd:63-65`)의 비율이 `isqrt(공격자 AGI × 1,000,000)`이 되어, 공격자 AGI 2 이상·명중 708 이상이면 `hit_max`(1000, `data/rules/battle.json:4`)에 닿는다. 시험은 제출 전에 `BattleCalc.hit_p`로 1000임을 단언한다(`hit_max`를 바꾼 시험용 규칙 상수에서는 이 구성이 성립하지 않는다).
- 부여(상태이상·봉인): 기본 확률이 아니라 **최종 확률** `status_p`(`battle_calc.gd:74-79`: 기본 확률 × 행운 배율 × 취약도 × (1000 − 누적 내성), 끝에서만 0~1000으로 자름)가 1000이어야 한다. 정의 범위 안의 구성: 공격자 LUC − 대상 LUC ≥ 25(`status_luck` 20 → 행운 배율이 상한 1500, `battle.json:22-26`), 대상 취약도 3000(범위 끝, `battle_limits.gd:26`), 누적 내성 0, 대상에 상태이상 없음(있으면 우선순위에 따라 `ailment_blocked`, 06 §3.11). 이때 최종 확률 = `min(1000, mul(mul(chance, 1500), 3000))`이고 기본 확률 223 이상이면 1000이다. 새 스킬 Lv1의 가장 작은 기본 확률은 실드 배시 250(→ 375 → 1125 → 1000). 피해 스킬의 부가 효과는 맞고 대상이 살아 있을 때만 판정하므로(06 §3.9 판정 순서) 위 명중 구성과 큰 HP를 함께 둔다. 시험은 제출 전에 `BattleCalc.status_p`로 1000임을 단언한다. M2 마무리의 모든 스킬 시험이 쓰는 구성(`test_battle_skills_all.gd`의 `_make_sure_targets`: 대상 AGI 1·런타임 취약도 `SURE_VULN` 1,000,000, `_make_tough`: HP 100,000)도 같은 결과를 낸다(범위 밖 값이지만 정의가 아니라 시험 중의 전투 유닛에만 쓴다).
- 정의 그대로(구성 없이)는 결과가 어느 쪽이든 그에 맞는 상태인지만 본다(걸렸으면 상태가 있고, 버텼으면 `*_resisted`와 상태 그대로).

### 10.4. 장면 시험 (`tests/test_party_menu.gd`, G-B)

05 §11.2 실행기 경로(프레임 대기·임시 폴더).

### 11.4. 인계 주의

- **수치를 맞추지 않는다**(D15): 시험이 실패하면 기능 결함을 고친다. 수치를 바꿔 승패를 맞추는 수정은 하지 않는다. 자리표시 수치를 바꿔야 할 기능상 이유(범위 위반 등)가 있으면 이 문서를 먼저 고친다.
- **값을 한 곳에서**: 능력치는 §6 `profile`, SP는 §4.1 식, 범위는 `BattleLimits`, 장착·배분 판정은 규칙 함수와 저장 검사가 같은 함수. 화면은 읽기 함수(`profile`·`learn_block`·장착 가능 이유)만 부르고 따로 계산하지 않는다(02 §4.3).
- **따로 단언할 것**: `profile`·`members()`의 객체 독립과 일반 공격 사본(`ClassDef.attack` 불변, §10.1), 이전의 머리 보존(§10.2), 1판 이전의 전투 시작 횟수(§10.2) — 상태 해시로 잡히지 않는다(06 §11.4와 같은 이유).
- **부식 글리프 상실**은 이전 정책이다(§8.4, 조정자 결정). 「2판 저장을 옮기면 부식 글리프 명령이 거부된다」를 결함으로 고치지 않는다.
- **실행한 것·하지 않은 것**(3판): 이 문서 작성자는 1판~3판 동안 Godot·시험·웹 확인을 직접 실행하지 않았다. 문서의 수치(경험치 표·레벨 표 표본·시작 장비 합·§10.1 확률 구성·§10.5 승리 경로의 몫)는 일회용 파이썬 식과 손 계산으로 확인했다. 구현 쪽에서는 G-A가 전체 헤드리스 시험(414/414)과 `small` 한 번을 실행했고 조정자가 다시 실행해 같은 결과를 확인했다(§11.3). G-A는 레벨 표·경험치 표가 §3.2·§3.3 표본과 같음을 확인했고(`test_growth_data.gd`), 검토는 직업 표 값 960개를 §3.3 식과 대조했다. 아직 실행하지 않은 것: `web_check`(G-B, 웹 내보내기 필요), 휴대폰 실기 확인(G-C). 디버그 `battle_finish`가 거부 때 자동 저장하지 않는다는 화면 쪽 시험(§10.1 「살아 있는 아군 0·끝 거부」의 마지막 문장)은 `battle_layer.gd` 소관이라 G-B가 맡는다.

## 13. 미확인 사항과 고려한 대안

### 13.1. 미확인·근거가 약한 곳

- **경험치 나누기**: 원작 1편이 적 경험치를 **파티 인원으로 나누는 것**은 확인됐다([W04] I 몬스터 표의 EXP 설명 「総計数値。PT人数で分配される」, 독립 검토가 2026-10-18 원문을 열어 확인. 이 문서 작성자는 같은 날 HTTP 403으로 직접 열지 못했다). **미확인**은 그 「인원」에 전투 불능 대원을 넣는지(분모 처리)와 다른 작품의 방식이다. 전투 불능 대원이 받지 못하는 것은 V에서 확인된다(R2 §2.12 [W24]). 그래서 「÷ 살아 있는 인원」(D19 ②)은 원작 근거 둘을 이은 사용자 결정이고, 「÷ 5 고정」(1판 ①)과 「각자 전부」(③)는 자체 제안·대안이었다. 정수 버림·나머지 버림도 자체 규칙이다(§3.1).
- 원작의 레벨업 때 HP·TP 처리(늘어난 만큼인지 가득인지), 스킬 배분의 확정 방식(누를 때마다인지, 나갈 때 확인인지), 선행이 레벨마다 다시 필요한 경우가 있는지는 확인하지 않았다(§3.4·§4.2·§4.6은 자체 규칙).
- 장비 칸: R2 §2.3은 「통상 4칸, 부위별 의무 장착 아님, I는 장신구 복수」까지만 확인했다. 작품별 정확한 칸 규칙과 전 장비 착용 행렬은 미확인(R2 §5-6). 장신구 둘까지·가방 99는 자체 값이다.
- 레벨 표·경험치 표·스킬 레벨 값·장비 수치는 모두 자리표시다(D15). 원작 대응 수치를 맞추지 않았다.
- 코드 행 번호: 3판에서 고친 곳(§3.4 HP·TP 규칙, §4.6·§5.7·§6의 함수, §7.5·§7.8의 오류 문구, §8.4의 파티 다름 거부, §10.7의 표 밖 고침·새 시험, `finish` 거부 규칙 `battle_rules.gd:593-595`)은 G-A 구현 작업 트리(2026-10-18) 기준이다. 그 밖의 줄은 구현 전(`e42ff92` + M2-B 작업 트리) 기준으로, 「무엇을 바꾸는가」를 가리키는 기록이다. `battle_layer.gd`·`dungeon_screen.gd`는 G-B가 고치면 바뀐다.
- 이 문서를 쓰며 Godot·시험·웹 확인을 실행하지 않았다(§11.4).

### 13.2. 고려한 대안

- **마스터리를 M2 스킬의 선행으로(원작 1편 계보, D18 ②)**: 원작 감각에 가깝다. 초기 SP 3(01 §5)과 모순되지는 않는다 — 시작 파티가 마스터리 1 + M2 스킬 둘만 들고 시작하면 Lv1 SP 3을 지키고, 시작 레벨을 Lv2 이상으로 두는 것도 「Lv1 초기 SP 3」과 어긋나지 않는다. 차이는 둘이다. ① **첫 플레이 구성**: 시작 파티가 M2 스킬을 덜 들거나(전투 화면·정책이 쓰는 스킬이 처음에 없음) 시작 레벨이 Lv1이 아니게 된다. ② **이전 정책**: 2판 저장을 옮길 때 잃는 스킬이 부식 글리프 하나가 아니라 직업마다 생기거나, 레벨을 올려 주는 이전 규칙이 따로 필요하다. 기존 전투 시험은 어느 쪽이든 전용 픽스처(성장 규칙 `initial_sp`를 크게, §10.7 `with_growth`·`party_with_skills`)로 지금 구성을 만들어 지킬 수 있으므로 시험 보존은 고르는 이유가 아니다. 사용자가 ①을 골랐다(§12).
- **SP를 저장**: 화면이 읽기 쉽지만 배운 레벨과 어긋날 수 있는 두 번째 값이 생긴다(06 §8.1이 HP·TP를 한 곳에 둔 것과 같은 이유로 버림).
- **스킬을 누를 때마다 바로 확정**: 단순하지만 사용자 요구(확정 전 취소 가능)에 맞지 않다.
- **장비를 개체(인스턴스)로**: 강화·소켓(후순위)에 필요하지만 지금은 같은 장비끼리 구별할 값이 없다. 개수만 센다.
- **장비 배율 보정을 곱하기로**: 06 §3.9 곱 순서 문제가 장비 사이에도 생긴다. 더하기로 정했다.
- **장비가 소재와 같은 가방**: 저장 2판 `materials`의 의미(소재 ID만)·상한이 바뀐다. 따로 두고 화면만 합쳤다.
- **임시 보급을 일반 화면에도 「시험용」으로 보임**: 휴대폰에서 주소를 바꾸지 않아도 되지만, 일반 플레이어 화면에 시험 기능이 남는다. 상점(M3)이 들어오면 지울 것이라 디버그에서만 보이게 했다. 보급 사용 여부를 저장에 표시하는 안은 지금 쓸 곳이 없어 넣지 않았다.
- **레벨업 때 가득 회복**: 승리 직후 회복이 휴식·여관의 역할과 겹친다(01 §1.3 원정 단위의 긴장).
